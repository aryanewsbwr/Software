B. DELIVERY CHARGE PRORATION (DEFINITIVE DATABASE PROOF):
--------------------------------------------------------------------------------
Question: Does the VB6 software charge the full month's delivery fee even when a
subscription starts or ends mid-month, or does it prorate by days active?

Database Audit Evidence (Live `billno20252026` table):
- Total non-null `Del_Amt` rows queried: 1,000+
- Total fractional/prorated `Del_Amt` rows found: 0
- Distinct `Del_Amt` values present: `[0, 5, 10, 20, 25, 30, 50, 100]` (all flat integers).
- Customer #1612 Case Study:
  * Subscription #74 (`dely = 20`, started `01/04/2025`, ended `07/05/2025` mid-month).
  * Subscription #75 (`dely = 5`, started `07/05/2025` mid-month, ended `14/08/2025`).
  * In April (only #74 active): `Del_Amt = 20` (full fee).
  * In May (both active mid-month): `Del_Amt = 25` (full 20 + full 5).
  * In June (only #75 active): `Del_Amt = 5` (full fee).

Conclusion: The legacy VB6 software charges the FULL month's delivery fee (a flat
monthly service charge) whenever a subscription is active during that billing month.
It does NOT prorate delivery fees by days active.

Implementation in `src/lib/billingEngine.ts`:

E. RATE OVERRIDE DAY-OF-WEEK SPECIFICITY & TIEBREAK:
--------------------------------------------------------------------------------
Actual Code in `src/lib/billingEngine.ts`:
```typescript
const getEffectiveRate = (publicaId: number, dayOfWeek: number, targetDateIso: string): number => {
  const matchingChanges = ratechanges.filter(rc => {
    const rPub = rc.Publica_id || rc.publica_id;
    const rDay = rc.Dayofweek !== undefined ? rc.Dayofweek : rc.dayofweek;
    const rDated = rc.Dated || rc.dated;
    const rDatedIso = parseLegacyDateToIso(rDated);
    return (
      rPub === publicaId &&
      (rDay === dayOfWeek || rDay === 0 || rDay === null || rDay === undefined) &&
      rDatedIso && rDatedIso <= targetDateIso
    );
  });

  if (matchingChanges.length > 0) {
    matchingChanges.sort((a, b) => {
      const dA = parseLegacyDateToIso(a.Dated || a.dated) || '';
      const dB = parseLegacyDateToIso(b.Dated || b.dated) || '';
      if (dB !== dA) return dB.localeCompare(dA); // 1. Most recent Dated DESC
      
      // 2. DAY-OF-WEEK TIEBREAK: exact match (1-7) strictly beats general (0)
      const dayA = a.Dayofweek !== undefined ? a.Dayofweek : a.dayofweek;
      const dayB = b.Dayofweek !== undefined ? b.Dayofweek : b.dayofweek;
      return (dayB === dayOfWeek ? 1 : 0) - (dayA === dayOfWeek ? 1 : 0);
    });
    const top = matchingChanges[0];
    return top.NewRate !== undefined ? top.NewRate : (top.new_rate !== undefined ? top.new_rate : (top.newrate || 0));
  }

  // Fallback: standard rate table for (pubId, dayOfWeek)
  const stdRate = rates.find(r => {
    const rPub = r.Publica_id || r.publica_id;
    const rDay = r.Dayofweek !== undefined ? r.Dayofweek : r.dayofweek;
    return rPub === publicaId && rDay === dayOfWeek;
  });
  if (stdRate) {
    const val = stdRate.Rate !== undefined ? stdRate.Rate : stdRate.rate;
    if (val !== undefined && val !== null && val > 0) return Number(val);
  }

  const anyRate = rates.find(r => (r.Publica_id || r.publica_id) === publicaId);
  if (anyRate) {
    const val = anyRate.Rate !== undefined ? anyRate.Rate : anyRate.rate;
    if (val !== undefined && val !== null && val > 0) return Number(val);
  }

  const warnMsg = `[BillingEngine WARN] Missing rate for publication #${publicaId} on date ${targetDateIso} (DayOfWeek: ${dayOfWeek}). Returning 0.00.`;
  console.warn(warnMsg);
  missingRateWarnings.push({
    publica_id: publicaId,
    date: targetDateIso,
    day_of_week: dayOfWeek,
    message: warnMsg
  });
  return 0.0;
};
```

G. SIGN CONVENTION SPECIFICATION (Due_Amt vs. Balance):
--------------------------------------------------------------------------------
Question: In the actual VB6 database and in the new engine's code, does negative or
positive represent "customer has a credit/advance" consistently, for both Due_Amt
and Balance? Or do they use different conventions?

Answer & Direct Proof from the Live Database:
In the legacy Access/VB6 schema, `Due_Amt` and `Balance` use OPPOSITE mathematical
sign conventions because they represent two distinct accounting perspectives:

1. `billnoYYYYYYYY.Due_Amt` (Arrears / Receivables Perspective):
   - Definition: "How much money is DUE from the customer?"
   - Positive (> 0): Customer owes money (ARREARS / UNPAID DUES).
     * Customer #108:  `Due_Amt = 537.00` (Customer owes ₹537 from FY 2024-2025).
     * Customer #1384: `Due_Amt = 135.00` (Customer owes ₹135 from FY 2024-2025).
     * Customer #1480: `Due_Amt = 145.00` (Customer owes ₹145 from FY 2024-2025).
   - Negative (< 0): Customer has pre-paid / is in credit (ADVANCE / CREDIT).
     * Customer #1612: `Due_Amt = -8.00`  (Customer holds an ₹8 pre-existing credit).
   - Zero / Null   : Account in perfect balance.

2. `billnoYYYYYYYY.Balance` (Customer Ledger Balance Perspective: Receipts - Bills):
   - Definition: Net cash balance remaining in customer's account after payments:
     `Balance = SUM(Receipts) - SUM(Bills)`
   - Negative (< 0): Customer is in DEFICIT (OWES money / Arrears).
     * Customer #108 in April:  `Balance = -537.00`  (Owes ₹537).
     * Customer #108 in May:    `Balance = -1086.00` (Owes ₹1086).
     * Customer #1384 in April: `Balance = -135.00`  (Owes ₹135).
     * Customer #1480 in July:  `Balance = -5.00`    (Owes ₹5 underpayment).
   - Positive (> 0): Customer is in SURPLUS (CREDIT / ADVANCE).
     * Customer #1612 in April: `Balance = 8.00`   (Holds ₹8 advance credit).
     * Customer #1480 in April: `Balance = 5.00`   (Paid ₹150 for ₹145 bill -> ₹5 advance credit).
     * Customer #1384 in Sept:  `Balance = 150.00` (Overpaid by ₹150 in Aug -> ₹150 advance credit).
   - Zero (= 0.00): Fully cleared / settled (no dues, no advance).

MATHEMATICAL IDENTITY:
  `Due_Amt = -Balance`
When a customer owes ₹100:       `Due_Amt = +100.00`, `Balance = -100.00`
When a customer has ₹50 credit:  `Due_Amt = -50.00`,  `Balance = +50.00`

NEW ENGINE IMPLEMENTATION (`src/lib/billingEngine.ts`):
- The `previous_due` parameter represents the receivable amount (`Due_Amt` perspective):
  * Positive value represents outstanding dues owed by customer (added to bill total).
  * Negative value represents pre-paid credit/advance (deducted from bill total).
- This aligns 100% with `billnoYYYYYYYY.Due_Amt`.

2. ARCHITECTURAL INVARIANTS
================================================================================
1. Transaction-Derived State: Bills and ledgers are derived deterministically from primary
   operational records (deliveries, holidays, suspensions, rate matrices, and receipts).
2. Zero Discount Stacking: Subscription-specific discounts strictly supersede customer-level
   defaults. Discounts never compound or stack.
3. Financial Year Boundary: Billing tables are partitioned annually (`billnoYYYYYYYY`,
   `billYYYYYYYY`, `receiptYYYYYYYY`). Opening balances for each FY are anchored by the
   `Month = 'Dues'` row in `billnoYYYYYYYY`.
4. Static Baseline Immunity: `Customer.dueamount` is a static 2007 baseline field created
   when the customer was first registered. It is NEVER used as the active opening balance
   in ongoing financial years.

3. COMPLETE MATHEMATICAL BILLING FORMULAS (FORMULAS 1 THROUGH 8)
================================================================================

FORMULA 1: DAILY NEWSPAPERS (दैनिक समाचार पत्र)
-----------------------------------------------
For each calendar day d in the billing month (d from 1 to Total_Days_In_Month):
  Deliver Day d IF AND ONLY IF ALL of the following 5 conditions are satisfied:
    1. Start Date Check:        Target_Date >= cd.s_date
    2. Cancellation Check:      (cd.c_date is empty OR Target_Date < cd.c_date)
    3. Holiday Check:           Target_Date is NOT in Holidays:
                                NOT (Holiday.oc_date == Target_Date AND
                                     (Holiday.publica_id == 0 OR Holiday.publica_id IS NULL OR Holiday.publica_id == cd.publica_id))
    4. Discontinuation Check:   Target_Date is NOT in Discontinue:
                                NOT (Discontinue.customer_id == cd.customer_id AND
                                     Discontinue.publica_id in (0, cd.publica_id) AND
                                     Target_Date in [Temp_From .. Temp_To/Forever])
    5. Delivery Schedule Check: DayOfWeek(Target_Date) in Schedule(cd.from_day)

  Daily_Paper_Total = Sum(Delivered_Days_at_Rate_R) * Rate_R * cd.qty


FORMULA 2: WEEKLY MAGAZINES (साप्ताहिक पत्रिका)
-----------------------------------------------
Delivered on publication's designated weekday (`pub.magzine_day`: 1=Sun, 2=Mon... 7=Sat).
  Delivered_Copies = Count of calendar dates d in month where:
    DayOfWeek(d) == pub.magzine_day
    AND Target_Date >= cd.s_date
    AND (cd.c_date is empty OR Target_Date < cd.c_date)
    AND Target_Date is NOT in Discontinuation range:
        NOT (Discontinue.customer_id == cd.customer_id AND
             Discontinue.publica_id in (0, cd.publica_id) AND
             Target_Date in [Temp_From .. Temp_To/Forever])
    AND Target_Date is NOT in Magazine-Specific Holiday (Holiday.publica_id == pub.publica_id)

  Weekly_Paper_Total = Delivered_Copies * Effective_Rate * cd.qty


FORMULA 3: FORTNIGHTLY & BI-MONTHLY PERIODICALS (पाक्षिक पत्रिका)
-----------------------------------------------------------------
Delivered on the 1st and 16th of the billing month.
  Delivered_Copies = Count of dates in {1st, 16th} where:
    Date <= Total_Days_In_Month
    AND Date >= cd.s_date
    AND (cd.c_date is empty OR Date < cd.c_date)
    AND Date is NOT in Discontinuation range:
        NOT (Discontinue.customer_id == cd.customer_id AND
             Discontinue.publica_id in (0, cd.publica_id) AND
             Date in [Temp_From .. Temp_To/Forever])

  Fortnightly_Paper_Total = Delivered_Copies * Effective_Rate * cd.qty


FORMULA 4: MONTHLY & QUARTERLY MAGAZINES (मासिक एवं त्रैमासिक)
--------------------------------------------------------------
Delivered on the 1st of the billing month.
  Eligibility:
    - Monthly Magazines: Delivered in all 12 months.
    - Quarterly Magazines (e.g., pub_id = 75): Delivered ONLY in Months {1 (Jan), 4 (Apr), 7 (Jul), 10 (Oct)}.

  Delivered_Copies = 1 IF:
    Eligible for Month
    AND Month_Start >= cd.s_date
    AND (cd.c_date is empty OR Month_Start < cd.c_date)
    AND 1st of month is NOT in Discontinuation range:
        NOT (Discontinue.customer_id == cd.customer_id AND
             Discontinue.publica_id in (0, cd.publica_id) AND
             Month_Start in [Temp_From .. Temp_To/Forever])
  ELSE:
    Delivered_Copies = 0

  Monthly_Paper_Total = Delivered_Copies * Effective_Rate * cd.qty


FORMULA 5: DELIVERY CHARGES (वितरण शुल्क)
-----------------------------------------
Defined per subscription line item in `Customer_Detail`:
  Total_Delivery_Charge = Sum of cd.dely for all active subscriptions in billing month
  (Stored in `billnoYYYYYYYY.Del_Amt`)


FORMULA 6: LINE & TOTAL DISCOUNT (छूट)
--------------------------------------
For each subscription line item i:
  Effective_Discount_Percent = (cd.dis > 0) ? cd.dis : ((cust.discount > 0) ? cust.discount : 0)
  Line_Discount = Line_Paper_Total * (Effective_Discount_Percent / 100)
  Total_Discount = Sum of Line_Discount for all customer subscriptions
  (Stored in `billnoYYYYYYYY.Dis_Amt`)

Constraints:
  - Subscription discount and Customer discount NEVER stack.
  - Discount applies ONLY to Line_Paper_Total.
  - Discount NEVER applies to Delivery Charges, Previous Dues, or Counter Sales.


FORMULA 7: PREVIOUS DUE & FINANCIAL YEAR BOUNDARY (पूर्व बकाया)
---------------------------------------------------------------
When calculating Previous Due for Month M:
  1. FY Opening Anchor:
     Year_End_Dues = billnoYYYYYYYY.Due_Amt (where Month = 'Dues')
  2. Prior Billed Charges in Current FY:
     Sum of [ Month_Paper_Total + Month_Del_Amt - Month_Dis_Amt ] for all months prior to M in current FY.
  3. Prior Receipts Collected in Current FY:
     Sum of [ MalRecpAmt + LessAmt ] from `receiptYYYYYYYY` recorded before Month M.
  4. Formula:
     Previous_Due(Month M) = Year_End_Dues + Prior_Billed_In_FY - Prior_Receipts_In_FY
  (Stored in `billnoYYYYYYYY.Due_Amt` or reflected in `Balance`)


FORMULA 8: OPENING BALANCE, CHARGES & TOTAL PAYABLE (कुल देय राशि)
------------------------------------------------------------------
The billing engine and legacy schema compute three separate values for each bill:

1. Opening_Balance_This_Bill:
   - Carried forward from prior month / FY anchor row:
     `Opening_Balance_This_Bill = Previous_Due`
   - In `billnoYYYYYYYY`:
     * `billno.Balance` stores this opening balance as:
       `Balance = -Previous_Due`  (Deficit/Arrears = Negative, Advance/Credit = Positive)
     * `billno.Due_Amt` is NULL for regular monthly bills (only populated in the FY anchor row `Month = 'Dues'`).

2. Current_Month_Charges:
   - Net charges incurred by customer during the billing month:
     `Current_Month_Charges = Total_Paper_Amount + Total_Delivery_Charge - Total_Discount`

3. Total_Payable_This_Bill (Grand Total Net Amount Due):
   - The actual grand total printed on the customer's bill slip as what they owe:
     `Total_Payable_This_Bill = Opening_Balance_This_Bill + Current_Month_Charges`

4. DISCOUNT PRIORITY & STACKING CONFLICT RESOLUTION
================================================================================
A. DATABASE COLUMNS INVOLVED:
   1. Subscription-level: `cd.dis` in `Customer_Detail`
   2. Customer-level:     `cust.discount` in `Customer` master
   3. Bill summary:       `billnoYYYYYYYY.Dis_Amt`

B. RESOLUTION HIERARCHY:
   - Case 1: Subscription has explicit discount (cd.dis > 0) -> Effective = cd.dis.
   - Case 2: Subscription has 0/null, customer has global discount -> Effective = cust.discount.
   - Case 3: Neither set -> Effective = 0.
   - Strictly NO compounding, NO summing (e.g. 10% global + 15% line item = 15%, NOT 25%).


================================================================================
5. DISCONTINUATION RULES (PERMANENT 'P' AND TEMPORARY 'T')
================================================================================
1. Permanent Discontinuation ('P'):
   - Effective from `temp_from` onward indefinitely.
   - Target_Date is discontinued if `Target_Date >= temp_from`.

2. Temporary Discontinuation ('T'):
   - Effective during interval `[temp_from .. temp_to]`.
   - Target_Date is discontinued if `Target_Date >= temp_from AND Target_Date <= temp_to`.

3. General Suspension (`publica_id = 0`):
   - Suspends ALL publications for the customer during the period.

4. Publication-Specific Suspension (`publica_id > 0`):
   - Suspends ONLY the designated publication; all other papers/magazines continue delivery.


================================================================================
6. HOLIDAY SCOPE & GENERAL PRESS HOLIDAY IMPLEMENTATION
================================================================================
A. General Press Holidays (`publica_id = 0` or `NULL`):
   - Nationwide printing press closure (Diwali, Holi, Independence Day).
   - Applies to ALL daily newspapers. No customer receives daily papers on these days.

B. Magazine Holidays (`publica_id > 0`):
   - Pre-printed periodicals do NOT skip on general press holidays.
   - They skip ONLY if a holiday record specifically targets that magazine (`Holiday.publica_id == pubId`).

7. LEDGER ROLLOVER, STATIC BASELINE IMMUNITY, & THE "8 MISSING CUSTOMERS" CASE
================================================================================
A. The ₹864,447 Lesson:
   - `Customer.dueamount` is a static 2007 baseline field.
   - Reading `Customer.dueamount` in ongoing financial years was the root cause of the
     historic ₹864,447 discrepancy. It is strictly excluded from active FY billing.

B. The FY Anchor Row:
   - Every financial year table (`billnoYYYYYYYY`) contains an anchor row where `Month = 'Dues'`.
   - `Due_Amt` in this row stores the audited March 31st closing balance.

C. Fallback Chain for the "8 Missing Rollover Customers":
   If customer HAS a `Month = 'Dues'` row in current FY table:
       Year_End_Dues = billnoYYYYYYYY.Due_Amt (where Month = 'Dues')
   Else If customer exists in Prior FY table (`billno(Prior_FY)`):
       Year_End_Dues = billno(Prior_FY).Balance [March] (live lookup from previous year)
   Else:
       Year_End_Dues = Customer.dueamount (only for brand-new customers created in current FY)

   CRITICAL: `Year_End_Dues` and `Customer.dueamount` are NEVER summed together.
